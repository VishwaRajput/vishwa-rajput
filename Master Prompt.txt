- Main animation orchestration system.

- Pinned sections where appropriate.
- Complex timelines, staggered reveals, text choreography, and section transitions.
- Coordinated entrance and exit animations.
- Shared timeline conventions and reusable animation utilities.

**Framer Motion / Motion for React**
- Component-level interactions.
- Page transitions where appropriate.
- React-native animation patterns.
- Hover states, interactive elements, layout transitions, and smaller UI animations.

- Subtle, high-quality 3D visuals.
- Abstract technical environments, spatial elements, or restrained WebGL effects.

Use WebGL only where it adds meaningful value. It must never be required to understand my content or navigate the website.

**Anime.js**
- Use selectively for specialized text or decorative animations when it provides a clear benefit.

- Use for a small number of carefully optimized visual effects, such as subtle atmospheric backgrounds, procedural gradients, or abstract data-inspired visuals.

- Use one shared scroll system.

### Animation performance

Use GSAP as the primary orchestrator for complex, coordinated sequences and Motion for independent React interactions.

Create a consistent animation architecture with:

- Reusable animation presets.
- Shared easing conventions.
- Consistent durations and stagger intervals.
- Centralized scroll-trigger configuration.
- Proper cleanup of timelines, observers, and event listeners.
- Correct React lifecycle handling.
- Responsive animation variants.
- Reduced-motion alternatives.

Never let two animation libraries simultaneously control the same property on the same element unless the interaction is explicitly coordinated.

Do not install every library merely because it is listed here. If a dependency is unnecessary, incompatible, or too expensive for the benefit it provides, explain the decision and choose the lighter solution.

## 8. PERFORMANCE IS A FIRST-CLASS REQUIREMENT

The site must look sophisticated without becoming unnecessarily heavy.

Prioritize Core Web Vitals and perceived performance from the beginning, not as an afterthought.

### Performance targets

Aim for the following on representative production builds and mobile test conditions:

- **Largest Contentful Paint (LCP):** 2.5 seconds or less.
- **First Contentful Paint (FCP):** 1.8 seconds or less.
- **Cumulative Layout Shift (CLS):** 0.1 or less.
- **Interaction to Next Paint (INP):** 200 milliseconds or less.
- Minimal unnecessary JavaScript.
- Fast initial rendering.
- Stable layouts and responsive image delivery.

These are targets, not guarantees. Measure real results and identify environmental factors that affect them.

### Optimization requirements

1. Prefer Server Components for static and content-heavy sections.
2. Avoid making the entire application a Client Component.
3. Use dynamic imports for heavy, nonessential interactive features.
4. Load Three.js, shader effects, and other WebGL dependencies only when necessary.
5. Defer noncritical animation initialization until it is useful.
6. Do not lazy-load the actual LCP image if it is the initial hero image.
7. Use `priority` or the appropriate current Next.js image-priority mechanism only for the genuinely critical image.
8. Optimize image dimensions, formats, and responsive source sizes.
9. Reserve image and media dimensions to prevent layout shifts.
10. Avoid loading multiple font families and unnecessary font weights.
11. Subset fonts when practical and use efficient font-display settings.
12. Avoid large client-side data dependencies.
13. Minimize unnecessary React re-renders.
14. Use `transform` and `opacity` for animation whenever possible.
15. Avoid repeatedly animating layout-intensive properties.
16. Avoid expensive filters, giant blur effects, and full-screen shader loops.
17. Pause or reduce offscreen animation and rendering.
18. Reduce rendering resolution and visual complexity on weaker devices.
19. Respect browser visibility and device constraints.
20. Avoid excessive observers, event listeners, and scroll callbacks.
21. Clean up all animation contexts, timelines, listeners, and WebGL resources.
22. Prevent layout shifts during fonts, photographs, loading screens, and page transitions.
23. Avoid adding dependencies that duplicate existing functionality.
24. Test the production build rather than relying exclusively on the development server.

### WebGL fallback

The website must remain attractive and functional without WebGL.

Provide a lightweight CSS fallback and avoid making 3D rendering necessary for the primary visual experience.

On low-powered devices, consider disabling nonessential 3D effects entirely.

### Loading strategy

The initial viewport should prioritize:

1. Essential HTML and CSS.
2. The main headline and introductory content.
3. The critical photograph, if used in the hero.
4. Essential fonts.
5. Interactive functionality needed immediately.

Load secondary animations and heavy visual effects after the critical experience is available.

Do not preload every image, font, shader, or JavaScript bundle.

### Performance verification

Use Lighthouse, browser performance tools, and available build-analysis tools to identify bottlenecks.

Where possible, inspect bundle sizes and document the impact of heavy dependencies.

Do not claim that performance targets have been achieved unless they have actually been tested.
